# 0001. 单文件 Monolithic UserScript 架构

## 状态
已接受 (Accepted)

## 上下文
JavdbEmbySkin 脚本体量已超过 25,000 行原生 JavaScript。在前端工程化主流观点中，通常会将此类超大型项目拆分为多模块（ES Modules/TypeScript），并通过 Webpack、Rollup 或 Vite 编译打包输出。我们需要决定项目的开发与维护形态。

## 决策
我们决定**维持单文件纯原生 JavaScript 架构（Monolithic UserScript）**，不引入复杂的 NPM 打包构建流水线，亦不拆分为通过 `@require` 外部加载的子脚本。

## 原因与权衡
1. **沙箱环境与 GM API 特权隔离**：Tampermonkey 的 `@require` 脚本运行在更宽松或独立的局部作用域中，若通过 `@require` 分离模块，会导致 `GM_xmlhttpRequest`、`GM_setValue` 等高级扩展 API 无法无缝跨模块调用，或者需要频繁通过全局 `window` 桥接，破坏沙箱安全性。
2. **离线与弱网高可用**：外部 `@require` 依赖第三方 CDN 或 GitHub 镜像，若遇到网络防火墙阻断、CDN 投毒或响应超时，整个皮肤将完全无法启动。单文件内聚保证脚本安装后在任何离线/弱网环境下 100% 可用。
3. **分发与更新确定性**：用户通过 GreasyFork 或手动更新时，单文件能确保所有视图逻辑、数据库迁移逻辑和样式表处于严格匹配的同一个微版本号下，彻底避免因客户端缓存旧子模块而引发的非对称运行时崩溃（Asymmetric Runtime Desync）。
4. **AI 维护友好性**：现代长上下文 LLM 可以一次性加载并理解全部上下文与函数调用链路，单文件结构避免了深层目录跳转丢失上下文的弊端。

## 结果与影响
* **收益**：安装零外部网络依赖、版本确定性强、无构建工具链故障。
* **代价**：单文件行数庞大，开发者与 AI 必须严格依靠全局命名空间与模块注释边界（如 `/* === Module Name === */`）自律组织代码，杜绝全局变量污染。
