# 0013. 皮肤关闭态原生网格（CSS Grid）恢复与布局引擎启闭熔断架构

## 状态
已接受 (Accepted)

## 上下文
在 v7.326 ~ v7.327 引入官方 Logo 与左下角悬浮切换按钮后，用户反馈了一个严重的视觉回归问题：
> “关闭 Emby 皮肤后，访问 JAVDB 主页再切回原生，卡片排版严重错乱、向右偏移且伴随大面积空白。”

### 1. 初始错误定性与过度设计方案（反模式回顾）
在面对该排版错位问题时，最初的分析出现了**工程归因偏差与过度设计冲动**：
* **初始误判**：草率地将错位归咎于“`removeEmbyDOM()` 架构设计落后、全局 DOM 生命周期清理不够彻底”，并提出了一个**大动干戈的重构计划**——试图推翻重写 `removeEmbyDOM()`、重塑整个 SPA 路由监听与全部组件的卸载生命周期。
* **用户的关键警醒与第一性原理质询**：
  用户当即提出了深刻的质疑与纠偏：
  > “你这个改动计划会不会太大了甚至还有彻底重构 `removeEmbyDOM()`，你确定用第一性原理排查了需要这样做吗？是不是过度设计了？前面几个版本没有出现过这个情况的，反而是最近几个版本我让你增加以下 LOGO 问题就多起来了。之前健壮性都做得挺好的。”

这一质询促使我们立即中止激进的重构提案，回归纯粹的第一性原理与 CDP 实机现场物理图层排查。

### 2. 第一性原理现场排查与真因锁定
在 Chrome 实机中通过远程调试协议（CDP）检查原生主页错位卡片的 Computed CSS 与事件监听流，真相迅速浮出水面——**原有架构历经多个版本打磨，其健壮性与清理机制本来就非常完备，根本不需要大改底层架构**，核心矛盾仅仅是微观上的状态未闭环：
1. **容器类名遗漏**：`removeEmbyDOM()` 遍历 `.movie-list` 时清空了行内样式，但遗漏了移除 `.emby-masonry` 与 `.emby-dynamic-focus` 类名；
2. **异步事件暗中唤醒**：瀑布流引擎 `WaterfallEngine.layout()`、`WaterfallEngine.schedule()` 与 `restructureGrid()` 入口缺乏全局 `enabled` 启闭守卫；在用户关闭皮肤切回原生后，原生网页首屏图片异步加载触发的 `load` 事件，通过挂载的图片监听被动唤醒了脚本后台的排版调度，悄悄在原生卡片上重新写入了 `transform: translate3d(...)`；
3. **物理坐标系叠加冲突**：JAVDB 官方主页在现代版本中采用了原生 CSS Grid 布局（`display: grid; grid-template-columns: repeat(4, minmax(0px, 1fr));`）。CSS Grid 的网格单元排版与脚本写入的 `translate3d` 绝对偏移在渲染流水线中**相互叠加放大**，导致卡片集体向右飞出数十像素并留下大片空白。

## 决策

我们坚决**摒弃“以大重构掩盖排查不足”的过度设计，遵循第一性原理与极简主义，仅通过 6 行手术级微创代码建立“布局引擎启闭熔断与原生网格纯净恢复”机制**：

### 1. 容器类名彻底复原
在 `removeEmbyDOM()` 遍历 `.movie-list` 时，同步执行类名净化，使父容器 100% 回归纯净原生网格状态：
```javascript
ml.classList.remove('emby-masonry', 'emby-dynamic-focus');
```

### 2. 布局引擎四重入口启闭熔断（Circuit Breakers）
为所有异步排版计算与 DOM 重排入口设置全局 `enabled` 启闭熔断守卫，杜绝原生页面下的任何异步唤醒：
* `WaterfallEngine.layout(el)`: 头部注入 `if (!enabled) { unregister(el); return; }`，关闭态立即注销监听并熔断；
* `WaterfallEngine.schedule(el)`: 头部注入 `if (!enabled) return;`，彻底丢弃所有异步排版任务；
* `ensureLayoutClasses()`: 头部注入 `if (!enabled) return;`，关闭态绝不触碰 DOM 类名；
* `restructureGrid()`: 头部注入 `if (!enabled) return;`，关闭态坚决不重组原生网格。

### 3. 剔除副作用自愈黑魔法
* 彻底拔除防盗链修复中重设 `img.src = ''` 的破坏性刷新代码；
* 全面收敛至 `<meta name="referrer" content="no-referrer">` 静态标签与 `img.referrerPolicy = 'no-referrer'` 属性，零 DOM 抖动无感穿透 403。

## 备选方案权衡与否决原因

### 方案 A：推翻并全面重写 `removeEmbyDOM()` 与生命周期架构（被否决 ❌）
* **做法**：重构 25,000+ 行脚本中所有 UI 组件的卸载逻辑，引入大型全局卸载注册表与微任务排空队列。
* **否决原因**：
  1. **典型的过度设计（Over-engineering）**：原有 `removeEmbyDOM()` 历经数万行代码演进与多轮严苛对抗式审计，其对女优气泡、设置遮罩、画廊面板、详情页多态封面等数十个子模块的清理本就稳定可靠。推翻重写将引入巨大的不确定性，极易引发难以预测的连锁次生 Bug；
  2. **药不对症**：即便重写了 `removeEmbyDOM()`，如果不给瀑布流引擎加上 `enabled` 熔断守卫，原生网页图片异步 `load` 依然会在清理后再次被动唤醒排版并写入 `translate3d`，错位依然会发生。

### 方案 B：手术级“类名净化 + 四重入口熔断”（被采纳 ✅）
* **做法**：抓住“CSS Grid + translate3d 叠加”的物理本质，仅补上 1 处类名清理与 4 处熔断条件（共 6 行代码）。
* **采纳原因**：以最小的代价、零架构扰动、极高的精准度彻底解决根本矛盾，最大程度保护了庞大代码库的健壮性。

---

## 工程哲学反思与启示

1. **避免把微观状态泄漏误诊为架构性缺陷**：
   在维护成熟、大规模（25,000+ 行）的代码库时，遇到新出现的异常，第一反应绝不应是“推倒重来”或“大架构重构”。这往往是用重构的疲于奔命来掩盖排查深度的不足。
2. **第一性原理高于经验直觉**：
   从浏览器的渲染力学（CSS Grid 布局规则、渲染树绝对位移计算、事件循环与图片异步 `load`）去推导现象的必然成因，才能找到“牵一发而动全局”的最小手术切入点。
3. **保持对已有成熟代码健壮性的敬畏**：
   原有系统在绝大多数场景下表现优秀，说明其基石稳固。新增功能引发的问题，必定是新增代码破坏了某种状态闭环，必须在闭环缺失处进行微创修补，而不是拆毁地基。

## 结果与影响
* **收益**：
  * 关闭皮肤后，JAVDB 原生主页 100% 恢复标准 4/5 列 CSS Grid，零类名污染、零位移残留；
  * 彻底切断原生模式下异步事件暗中唤醒脚本后台排版的通道，消除隐蔽的 CPU 占用与重排消耗；
  * 脚本左下角固定 56px 官方 Logo 切换按钮与原生页面完美共存；
  * 原有 25,000+ 行庞大架构的稳定性得到 100% 保全。
* **代价**：
  * 未来任何新增的异步布局管理器或 DOM 重塑逻辑，都必须在入口处遵循 `if (!enabled) return;` 熔断准则。
